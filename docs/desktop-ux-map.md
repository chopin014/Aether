# Aether desktop UX map

Audit date: 2026-10-23. Baseline: `7d68c26a1c`, plus the reviewed presence change
`bd996052a9`. This is a source and reference audit, not a claim that every workflow
has been exercised in the running app.

## Scope agreed with the user

Improve the UX first. Prefer existing Element features and SDK operations, including
features that Element exposes poorly. Presence controls are the example: a discoverable
profile action, honest status, feedback and retry are useful improvements without a new
service. Calling the existing SDK to apply a user's choice is in scope.

Do not redesign sync, add Sliding Sync, replace encryption, change the calling transport,
or introduce new server services in this phase. Features that require new shared data
models, providers or permission semantics stay in the decision queue. A Matrix mechanism
being possible does not, by itself, make that product mapping approved.

Keep each feature in its own reviewable commit. Implement clear equivalents directly;
ask about unresolved product semantics when that feature becomes the next work item.

## What the study establishes

The local study contains **99 capture states**, with screenshots, accessible trees and
geometry. Its `docs/coverage.md`, `docs/visual-spec.md` and `docs/element-desktop-plan.md`
live in the preparation workspace immediately above this checkout. Research assets remain
private and are not dependencies of this application or attachments to this document.

Use three evidence levels:

- **Observed:** the particular captured appearance and accessible controls. This includes
  empty pins and thread browsers, notification choices, profile menus, message menus,
  settings and administration pages.
- **Implementation choice:** adapting those controls to Element's working models. A capture
  does not prove pagination, delivery, persistence, permissions or cancellation behavior.
- **Unknown:** uncaptured transitions or products with no approved Matrix mapping. The original
  study did not capture populated/open/create thread workflows. The user's later populated-pin
  screenshot adds card-layout evidence, not network or permission behavior.

Measure CSS pixels, not screenshot pixels. Most captures use 1280 × 720 at DPR 1.5;
some, including Inbox and self-profile, use DPR 1. The study is primarily Portuguese and
dark, with a resized sidebar. Use Aether branding, licensed existing fonts and Compound
tokens rather than copying Discord's private assets, fonts or account content.

merely to show a short list. Mobile/narrow fallbacks must remain operable.

## Implementation order

1. **Current pass:** finish/review pins, thread browser/conversation and shared close ownership;
   ship the reviewed profile presence controls and unknown-status correction. Keep separate commits.
2. **Profiles and contextual actions:** quick/full profile separation, member action grouping,
   channel/message menus, reply/edit presentation, notification choice feedback.
3. **Find content:** side search using the existing search engine, supported suggestions,
   media/files and a truthful notification Inbox. Keep encrypted-index limits visible.
4. **Composition and media:** attachment/emoji/sticker surfaces, upload and failure states,
   reactions and polls using existing capabilities.
5. **Settings and administration:** reorganize current settings/controllers, channel/server
   editors and permissions with the captured navigation/spacing; preserve Matrix security tools.
6. **Calls and desktop polish:** existing device/permission/share affordances, call stage shell,
   keyboard/help/accessibility and platform behavior. Review embedded-call limits before deeper changes.

Backend-dependent features remain outside these waves. Split large waves into individual
features with their own review and tests; don't combine a navigation rewrite with unrelated
protocol or settings changes.

## Acceptance for each feature

- Validate the production component/adapter, not a disconnected static mockup. Screenshots
  alone do not prove behavior and passing unit tests do not prove layout.
- Check empty, loaded, long, loading, failed/retry, permission denied and unsupported states;
  add encrypted/redacted/undecryptable variants where message content is shown.
- Test open/toggle/close/Back/Escape, focus return, keyboard-only traversal and nested dialogs.
  Count close controls at the composed surface, not only inside an isolated header.
- Preserve query/scroll/drafts across appropriate transitions; discard stale async work on
  room/account changes and dispose listeners. Do not fabricate success or presence.
- Review dark/light, Portuguese expansion, narrow desktop, long names, zoom, scrolling,
  avatar/image bounds, high contrast and reduced motion where relevant.
- Cover real happy paths with disposable homeservers; never mutate the user's account,
  existing calls or reference session for testing. Do not regenerate screenshot baselines locally.
- Regenerate i18n, run affected types/lint/format/tests, inspect captures, and state limitations.
  Build shared components before previewing their changes; do not remove live `dist` mid-build.

## Further evidence needed

The study lacks full populated thread lifecycle, reliable full-screen media-viewer capture,
multi-person camera/share transitions, authentication/recovery reference and many error states.
Build controlled Matrix fixtures for these. Preserve Element's existing behavior until a
replacement has equivalent working coverage. Do not describe uncaptured Discord behavior
as observed or mark the whole product as visually equivalent.

Protocol reference: [Matrix Client–Server API](https://spec.matrix.org/latest/client-server-api/),
especially presence, threading, Spaces, room permissions, push rules and account data. This
phase uses the existing client implementations of those mechanisms. The source audit, not
the appearance of a Discord toggle, determines which actions can actually work.
